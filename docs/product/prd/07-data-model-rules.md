## 7. Data Model — Rules

Rules are stored **as code in git**, one versioned file per rule, and materialized at review time.

| Field | Type | Notes |
|---|---|---|
| `id` | string | Stable; the citation key. Never generated by a model at review time. *v0.12:* the `exemplar.` prefix is reserved for rules shipped in presets (FR-E19), as `bug.` is for bug classes. |
| `kind` | enum | `exemplar` (LLM agent) or `compiled` (deterministic) — *new* |
| `category` | enum | `Blocker` , `Security` , `Performance` , `Correctness` , `Style` , `Nit` |
| `severity` | enum | `blocking` , `important` , `suggestion` — drives ranking, the comment budget, and the Conventional Comments label. `blocking` describes the *finding* (a human reviewer would block on it), not the bot's behavior: the bot still never requests changes (§3.2), and `blocking` and Security findings are exempt from the comment budget (FR-P6) — *new* |
| `description` | markdown | Exemplars: the detection prompt. Compiled rules: human explanation shown in the comment. |
| `matcher` | object | Compiled rules only: `{engine: semgrep\\|ast-grep\\|codeql, rule: ...}` — *new* |
| `file_patterns` | glob[] | Include and negated globs; deterministic scope before any model call. |
| `applies_to` | object | *v0.11, proposed (FR-E17):* which repositories the rule runs on: `repos` (owner/name patterns) and `tags` (declared on the repository's config file); either matching selects it; absent means every enrolled repository. A repository's `disabled_global_rules` or a project's `disabled_rules` (FR-E20) still removes it. Language is not a tag: it stays in `file_patterns`. |
| `citation` | object | Config-as-code source, source comments, and doc URL if any. |
| `posting_mode` | enum | `per_occurrence` or `grouped` . |
| `fix_policy` | enum | `none` , `suggest` (emit suggestion block when local), `describe` — *new* |
| `owner` | string | Team or CODEOWNERS entry. |
| `status` | enum | `candidate` , `shadow` , `active` , `killed` . |
| `review_by` | date | **Expiry / re-validation date** (default 12 months after promotion; *v0.9:* `global.yaml` `review_by_defaults` sets one per category, since a Security rule and a Performance rule written against one library version have half-lives an order of magnitude apart). Past this date the rule drops to `shadow` unless the owner re-confirms or eval still passes on recent PRs — *new* (borrowed: AutoCommenter's suppression of outdated best practices) |
| `export` | object | Whether and how the rule is exported to coding-agent instructions (§10) — *new* |
| `eval_cases` | path | Positive and negative cases from real PRs, plus injected cases (§11). |

```yaml
# rules/performance/blocking-fetch-in-loop.yaml
id: blocking-fetch-in-loop
kind: exemplar
category: Performance
severity: important
owner: "@platform/runtime"
status: active
review_by: 2027-09-01
file_patterns: ["**/*.cpp", "!**/test/**"]
posting_mode: per_occurrence
fix_policy: suggest
description: |
  Blocking inside a high-frequency loop increases latency and causes thread
  exhaustion. When a FetchData call is made inside an async task, warn about
  latency and thread exhaustion. FetchData is acceptable as long as the task
  has already been awaited.
citation:
  doc: https://docs.internal/guidance/async
  comments: [{pr: 48213, comment_id: 991204}, {pr: 51877, comment_id: 1033412}]
export:
  agents: true          # include in AGENTS.md / CLAUDE.md / Copilot / Cursor exports
  summary: "Don't call FetchData inside an async task before the task is awaited."
eval_cases: evals/blocking-fetch-in-loop/
```

**Config layering** — *v0.12*: rules come from four layers, each owned by someone different:

1. **Presets** shipped with the binary (`exemplar:recommended`), owned by Exemplar's maintainers.
2. **The config repository**, owned by the platform team and rule owners through CODEOWNERS: the presets `global.yaml` extends, the organization's rules in `rules/` (narrowed by `applies_to`), and its presets in `presets/`.
3. **The repository's file** in the config repository (`repos/<owner>/<repo>.yaml`), owned by the platform team: enrolment, the kill switch, shadow, auto-approve and the other safety settings, and `disabled_global_rules`.
4. **The project's `.exemplar/`** in the target repository, owned by that repository's CODEOWNERS and read from the base branch only: `config.yaml` (FR-E20) and repository rules in `rules/`.

Effective config = the rules of every preset the organization or the project extends, plus the organization's rules whose `applies_to` matches the repository (all of them, when absent); minus the organization's `disabled_rules`, the repository file's `disabled_global_rules` and the project's `disabled_rules` (the last never removes a `required` rule); with `rule_settings` applied, the organization's first, then the project's, each only narrowing; plus the project's repository rules. A rule id defined twice is an error. Cached with a 15-minute TTL and invalidated on config pushes.

**Scope and inventory requirements** — *v0.11, proposed; see §4.1 and §16 question 18*:

- **FR-E17 Rule selection.** A rule in the config repository may declare `applies_to` with repository name patterns and tags; the repository config file may declare `tags`. A rule applies to a repository when `applies_to` is absent or either list matches, and the repository has not disabled it. Validation rejects a tag no enrolled repository carries and a pattern that matches none. A mined candidate's PR carries `applies_to.repos` set to the repositories its evidence came from; the owner widens it on merge. Selected rules live only in the config repository, never in a target repository's `.exemplar/rules`. A project may also opt in, by extending an `org:*` preset (FR-E20), and opt out; whether `org:*` presets and `applies_to` tags both remain, or one subsumes the other, is part of §16 question 18.
- **FR-E18 Per-repository inventory.** For any enrolled repository, the web UI and the CLI list the rules that run on it with the reason (global, selected by `repos` or `tags`, repository-local) and the global rules disabled there, computed from the same effective config the review uses. Config CI reports, on a rules PR, how many repositories a changed rule starts or stops running on. *v0.12:* the reasons also name the layer: the preset that brought the rule, and the layer that disabled or narrowed it. The inventory and the rule exports (§10) read the project's `.exemplar/config.yaml` at the base branch, so they show what a review would run; config CI's count of repositories a rule starts or stops running on says that it does not see project files.

**Layering requirements** — *v0.12; see the config layering above and §16 question 19*:

- **FR-E19 Presets and `extends`.** Exemplar ships named presets of rules inside the binary; their rule ids carry the reserved `exemplar.` prefix, so a new release never collides with an organization's rule. `global.yaml` may declare `extends`, a list of presets: `exemplar:<name>`, a preset defined in the config repository (`org:<name>`, from `presets/<name>/`, whose rules run only where a layer extends it), or a preset in another repository pinned to a commit (`github:<owner>/<repo>//<name>@<sha>`, read with the config repository's installation; a branch or tag is refused, the preset may not itself extend, and the pin changes only through a config PR). `disabled_rules` removes rules for every repository; `rule_settings` per rule id may set `status: shadow`, add `exclude_paths`, set `required`, which when true stops a project from disabling or narrowing the rule, set `owner` (the team that receives the rule's feedback, digest and adjudication; `global.yaml` `preset_owner` is the default for every preset rule), and set `history_from` to an organization rule id the preset rule replaces, so an installation that copied a starter rule keeps its acceptance, feedback and demotion history when it adopts the preset. Preset rules in the Security category or with `blocking` severity ship `required: true`; the organization may relax that with `required: false`. Neither layer changes a preset rule's severity or description. The learning plane acts on a preset rule through `rule_settings`: demotion and expiry write `status: shadow` there, since the rule has no file in the config repository. Presets move with the binary, but a preset rule becomes active only through the human gate (FR-L6): a rule a release adds runs in shadow until the organization raises `presets_accepted` in `global.yaml` to that release, a config PR whose CI lists the preset rules added, changed or removed since the accepted version. A rule a release removes stays in the preset as `killed` for one release so references to it still resolve. Config CI validates against the preset version the deployed exemplar-api reports as well as its own binary's, so a config cannot pass CI and fail to load in the cluster, and the config version a review records names the preset version, so a stored review still names the rule text it ran. A config without `extends` behaves as before.
- **FR-E20 Project configuration.** A target repository may carry `.exemplar/config.yaml`, read like the rest of `.exemplar/` from the base branch, never the PR head, so a PR cannot change its own review, and a PR that touches it is never auto-approved: `extends` (`exemplar:*` and `org:*` presets only, never a repository reference), `disabled_rules` (any rule the organization has not marked `required`), and `rule_settings` limited to `status: shadow` and `exclude_paths`. It cannot re-enable a rule the organization disabled, remove a preset the organization extends, or change enrolment, shadow, auto-approve, forks, drafts, context or any other setting of the repository's file in the config repository. A repository without the file gets the organization's defaults; a repository that is not enrolled is never read.
