## 11. Evaluation — *revised*

| ID | Requirement |
|---|---|
| FR-X1 | Every rule ships with positive and negative cases from real PRs. |
| FR-X2 | CI on the config repo runs `eval` mode and reports precision, recall and F1 per rule; merge requires thresholds. |
| FR-X3 | **Golden set** of historical PRs measures LGTM recall against the human baseline. |
| FR-X4 | Staged rollout: `shadow` → limited repos → general. |
| FR-X5 | Model or harness upgrades re-run the full golden set before switching. |
| FR-X6 | **Injected-violation evals** — *new* : mutate known-clean code to introduce a rule's violation (or a bug class for Lane 3) and measure detection. Recall is otherwise hard to measure because historical reviewers missed things too. |
| FR-X7 | **Replay harness:** run the full pipeline over historical PRs and compare with what human reviewers actually said, for shadow evaluation and pre-launch volume estimates. |
| FR-X8 | **In-house baseline reviewer** — *new* : since there is no vendor to compare against, build and maintain a deliberately simple baseline (one prompt, whole diff, same model) and run it in shadow on a random sample of PRs (default 10%, stratified by repo and size) rather than every PR. Exemplar must beat it on precision and on accepted findings per PR; if it doesn't, the extra machinery isn't earning its keep. |
| FR-X9 | **Verifier calibration:** a labeled set of findings (true / wrong / unimportant) measures the verifier's refutation accuracy; target ≥ 90% of known-wrong findings refuted with ≤ 10% of known-true findings refuted. |
| FR-X10 | **Adversarial eval set** — *new* : from Phase 0, a maintained set of PRs containing prompt injection in diffs, comments, PR descriptions, file names and linked tickets, each with the outcome an attacker wants (a false approval, a suppressed finding, a fabricated citation). The set runs in CI on every config, prompt or model change; any success fails the build. The Phase 5 red team extends this set rather than replacing it. *v0.12:* the set, and the verifier and categorizer calibration labels (FR-X9), ship with the binary and run against the shipped preset rules, so an installation inherits them and they do not depend on which rules it keeps; cases an organization adds in its config repository run alongside. |
| FR-X11 | **Eval cases for incident-derived rules.** Rules mined from postmortems and reverts (FR-L1.7) often have no review comment and no clean positive case. For these, FR-X1 is satisfied by the reverted or incident-linked diff as the positive case plus injected-violation cases (FR-X6); the config PR labels the rule `eval: synthetic` until a real PR provides a positive. |
| FR-X12 (not built: #273) | **Clean-PR false-alarm rate** — *v0.7*. A maintained set of PRs known to be clean (merged, never reverted, no incident within 90 days, and confirmed by an engineer who knows the code) is reviewed on a schedule with the current config, prompts and models. Every finding on it is a false alarm; a finding whose suggested fix would change behavior is a *harmful* false alarm and is reported separately. The rate is tracked per rule and per bug class, and a prompt, tool or model change is kept only if neither the incident-set score (FR-X11) falls nor this rate rises. *(Borrowed: Anthropic runs its reviewer on known-clean PRs and counts findings that would lead to a harmful change.)* |
| FR-X13 | **Synthetic cases run under an eval profile** — *v0.12*. A synthetic case, whose code is built from what the case carries and names no repository, runs under a built-in profile: the organization's global settings and rules (the shipped rules, for shipped cases), a repository configuration with posting on and auto-approve enabled for every path, and the policy inputs a synthetic workspace cannot supply (author history, ownership, branch rules, verifier calibration, merge-safety history) set to pass unless the case sets them. Everything the review computes from the diff, including findings, coverage and the model-derived Stage 2 categorization and confidence, runs for real. Eligibility is not consulted, since no repository is read, and the profile is refused for any workspace not built from the case. The set includes positive controls, harmless cases that must reach approval under the profile, so a false-approval case that could never fail is caught; they run with scripted model outputs, so they are deterministic and cost no model calls, while the adversarial cases run on live models. A recorded case (a real repository at a commit) keeps the eligibility check, and an ineligible repository is a counted failure, never a skip. Config CI passes with no repository enrolled. |
