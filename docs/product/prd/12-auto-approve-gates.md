## 12. Auto-Approve Gates

**Deterministic first. Expensive only if it all passes.**

**Stage 1 — cheap, strictly deterministic (all must pass, no model output consulted):** repository opted in and eligible (FR-H1); every changed path within the approved scope *and* outside the denylist (FR-A8); **all lanes ran to 100% coverage, including the bug lane (FR-A7), and the run is clean (FR-A13: no `blocking` or `important` finding and no Security-category finding; `suggestion` findings are posted alongside the approval)**; author in the repo's allowlist (FR-A6); **author has merged enough PRs in the touched paths (FR-A10)**; **the change stays within one ownership area and off the shared paths (FR-A11)**; not a fork PR; not a degraded or incomplete run (FR-D5); ≤ 10 files and ≤ 1,000 lines changed.

**Stage 2 — only if Stage 1 passes:** CODEOWNERS lookup; branch-protection lookup; `merge_safety_score ≥ 0.7` (deterministic, computed from history: churn, incident and revert proximity of the touched paths — definition in §16); LLM low-risk categorization verified by a second model per §8.2, yielding `review_confidence ≥ 0.8` → `APPROVE`.

*Changed in v0.6:* `review_confidence` and `merge_safety_score` were listed in Stage 1 but one is model-derived and the other was undefined; both move to Stage 2. "Title matches policy" is removed as a gate because the title is author-controlled input; it remains an informational check.

*Changed in v0.8:* author experience (FR-A10) and blast radius (FR-A11) join Stage 1, both computed from history and CODEOWNERS already stored, so the gate scopes trust to where it was earned without a hand-maintained list. *(Borrowed: Will Larson's `small-change` qualifies a PR only when its author has ten or more merged PRs in the affected service and the change touches fewer than N services, with shared libraries excluded; about 10% of changes qualified at the start.)* A caution from the same source: these gates work best for high-scale, low-domain-complexity software, where incremental rollout catches what review misses. For domain-heavy code (billing, policy, anything whose correctness depends on configuration a rollout doesn't exercise) keep `paths` narrow and `max_owner_areas` at 1, and let the counter-metrics (§13.1), not the qualifying share, decide when to widen.

| ID | Requirement |
|---|---|
| FR-A1 | Never `REQUEST_CHANGES` . |
| FR-A2 | **Compliance:** where two approvals are required the bot counts as at most one; exemptions are a hardcoded constant, not config. |
| FR-A3 | **Kill switch is a YAML edit** , effective within the 15-minute cache TTL (seconds with push invalidation). |
| FR-A4 | Every auto-approval records the full gate trace. |
| FR-A5 | **Ownership visibility** — *new* : auto-approved PRs touching a CODEOWNER's paths appear in that owner's weekly digest, preserving awareness even when no human reviewed. |
| FR-A6 | **Author policy** — *new* . The allowlist is per repo and names humans. PRs authored by bots or coding agents (Dependabot, Renovate, Copilot, Claude Code, internal agents — detected by account type, App identity or commit trailer) are not auto-approvable unless the repo explicitly allowlists that identity, and then only within a narrower scope (e.g. dependency manifests for Renovate). |
| FR-A7 | **The bug lane must have run.** On any PR that passes the rest of Stage 1, the bug lane is forced to run regardless of FR-E6's risk threshold. A clean run (FR-A13) only counts when every lane that could have found something actually ran. |
| FR-A8 | **Path denylist** — *new* . Regardless of approved scope, a PR touching any of these is never auto-approvable: `.github/**` and other CI/workflow definitions, `CODEOWNERS` , branch or ruleset configuration, build definitions, dependency manifests and lockfiles, the exemplar config repo, and the generated instruction files from §10 ( `AGENTS.md` , `CLAUDE.md` , `.cursor/rules/*` , `.github/instructions/*` ). The denylist is a hardcoded constant extended by config, never narrowed by it. A `**/*.md` scope therefore does not admit `AGENTS.md` . |
| FR-A9 (not built: #251) | **Approval revocation.** If a new push arrives after approval, the approval is dismissed (GitHub review dismissal) and the gates re-run on the new commit. An approval never carries forward. *(v0.9)* **The approval is bound to the base too.** It records the base branch SHA it was judged against. When the base has moved by more than `auto_approve.base_drift_commits` (default 20) or any commit on it touched a path the PR touches or imports, the `exemplar/merge-policy` check turns `pending` and the gates re-run against the new merge result before the PR can merge. Two PRs each approved against an old main must not be able to merge into a broken one. |
| FR-A13 | **A clean run** — *v0.9*. For Stage 1, a run is clean when it posted no `blocking` and no `important` finding and no Security-category finding of any severity. `suggestion` findings do not block approval; they are posted with it, and the gate trace (FR-A4) lists them. Requiring zero findings of any severity made a log-message nit as decisive as a blocking bug and shrank the eligible set without buying safety. *(Borrowed: Larson's `small-change` qualifies with no P1 or P2 findings; Anthropic clears low-risk changes with open nits.)* |
| FR-A10 (not built: #252) | **Author experience** — *v0.8*. A PR is auto-approvable only if its author has at least `auto_approve.min_author_merges` prior merged PRs (default 10) in each ownership area the change touches, counted from merged PR history over the last two years (FR-L1.1's lookback), human-authored PRs only, by the author's GitHub login. Experience is per area, not per repo: a long-time owner of one directory is new to another. The allowlist (FR-A6) stays for exceptions in both directions: an allowlisted author is exempt from the count, and a bot identity is governed by FR-A6 alone. The threshold is a floor config may raise and never lower below 1. The gate trace (FR-A4) records the count per area. |
| FR-A11 (not built: #252) | **Blast radius** — *v0.8*. A PR is auto-approvable only if it touches at most `auto_approve.max_owner_areas` ownership areas (default 1), where an area is one CODEOWNERS entry's path set on the base branch, and touches nothing under `auto_approve.shared_paths`: libraries, utilities and other code many areas import, listed per repo. Paths matching no CODEOWNERS entry count as one area each and are never auto-approvable unless the repo sets `auto_approve.unowned_paths: allow`. The ceiling is a constant config may lower and never raise above 3; `shared_paths` may be extended and never narrowed by a repo file. |
| FR-A12 (not built: #253) | **System accountability** — *v0.8*. An incident, revert or confirmed bug on a PR that Exemplar auto-approved is a defect in the gates, the reviewer or verification, never a finding against the author. Each is recorded against the approval's gate trace (FR-A4) with what should have caught it, appears in the audit board and the owner digest, and feeds §13.1. The triage question is "which gate, lane, rule or check should have refused this", and the fix lands in config, a rule, an eval case or the code. *(Borrowed: Larson's norm that any error caused by a `small-change` is a failure of the system, fixed at the system level.)* |
